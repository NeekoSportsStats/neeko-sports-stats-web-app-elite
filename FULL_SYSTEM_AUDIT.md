## EXECUTIVE SUMMARY

This audit examined the entire Neeko Sports Stats system: frontend, database, formulas, pipelines, and data flow. The system is **PRODUCTION-READY** with strong foundations, but has accumulated **technical debt** and **consistency issues** across multiple layers.

### System Health: ⚠️ YELLOW (Functional but needs attention)

**WORKING**:
- Frontend routing and lazy loading
- Premium/Free tier gating
- Database schema and RLS
- Core projection engine
- Market Watch data pipeline
- Rankings cache system

**NEEDS ATTENTION**:
- Formula consistency (3 different neeko_rating formulas)
- View/table contract mismatches
- Pipeline observability gaps
- Breakeven formula accuracy
- Value score computation

### 1.1 Routing Structure

**Main Entry**: `src/main.tsx` → QueryClient + AuthProvider + BrowserRouter

**Route Map**:

**✅ GOOD**: Lazy loading reduces initial bundle, proper auth guards
**⚠️ RISK**: No error boundaries on lazy components

### 1.2 Data Fetching Patterns

**AFLRankingsPage.tsx**:
- **Premium**: `.from("v_rankings_master").select(PREMIUM_COLUMNS)` — 60 columns
- **Free**: `.from("v_rankings_free").select(FREE_COLUMNS)` — 52 columns
- **Null Safety**: ✅ `((data as any[]) ?? []).map(normalizeRow)`

**MarketWatchPage.tsx**:
- **Query**: `.from(viewName).select("*").limit(limit)` — 100 free, 200 premium
- **Null Safety**: ✅ `(data ?? []).map(...)`
- **Column Mapping**: Manual mapping of 85 fields (lines 31-85)

**✅ GOOD**: Defensive null handling after recent fixes
**⚠️ ISSUE**: Hard-coded column lists can drift from actual view schemas

## PART 3: VIEW/TABLE CONTRACT AUDIT

### 3.1 Rankings Page Contract Mismatch

**Frontend Expectation** (AFLRankingsPage.tsx, line 330):
```typescript
PREMIUM_COLUMNS = "player_id,player_name,team,position,price,projection_final,
  ceiling,floor,consistency,neeko_rating,value_score,ai_recommendation,
  recommendation_short,matchup_label,..."
```

**Database Reality** (v_rankings_master):
- ✅ Has: All requested columns present
- ⚠️ Type mismatch: `projection_final` is NUMERIC in view, treated as number in frontend
- ⚠️ Naming: View has `team`, `team_name` — frontend expects `team`

**Status**: ✅ CONTRACT VALID (with minor type coercion)

### 3.2 Market Watch Contract Issues

**Frontend** (MarketWatchPage.tsx, line 38):
```typescript
breakeven: Math.round(r.projection_final ?? 0)
```

**Database** (v_mw_premium):
```sql
breakeven = COALESCE(pp.priced_at, ROUND(rc.price / 10490, 1))
```

**❌ CRITICAL MISMATCH**: Frontend overwrites database breakeven with `projection_final`!
- This defeats the fix in migration `20260313132217` (breakeven formula)
- Frontend should use `r.breakeven` directly, not recompute it

### 3.3 Edge Board Schema

**View**: `public.v_edge_board_safe` (10 columns)
- Selects 3 players (captain, breakout, trap) using CTEs
- Columns: player_name, team, position, neeko_rating, projection_final, etc.

**RPC**: `public.get_edge_board_data()`
- Returns pre-computed edge board from materialized view
- Used by: `src/features/afl/edge/AFLRoundEdgeBoard.tsx`

**✅ Status**: Contract valid, MV-backed for performance

## PART 4: PIPELINE & CRON AUDIT

### 4.1 Pipeline Architecture

**Master Controller**: `public.run_afl_pipeline_controller_internal()`
- Runs daily at 1 AM Melbourne time
- Orchestrates 4 stages:
  1. **Ingestion** (`run_afl_worker_ingestion`)
  2. **Processing** (`run_afl_processing_core`)
  3. **AI Enrichment** (`run_neeko_ai_enqueue`)
  4. **Output Refresh** (`refresh_rankings_and_market_watch`)

**Stage Breakdown**:

#### Stage 1: Ingestion (run_afl_worker_ingestion)
- Fetches player stats from AFL API
- Fetches match results
- Transforms raw JSON → `afl.raw_player_stats`
- Syncs to `afl.player_games`

#### Stage 2: Processing (run_afl_processing_core)
- Step 1-8: `afl.refresh_projection_engine()`
  - Builds `feature_player_form` (games_played, averages, consistency)
  - Computes `feature_price.value_score`
  - Populates `afl.player_projection`
  - Refreshes `afl.mv_player_projection` (MV with neeko_rating)
- Step 9-14: Role signals, matchup multipliers, breakout models
- Step 15: `afl.refresh_player_rankings_cache()` — populates cache
- Step 16-19: Accuracy tracking, market watch snapshot

#### Stage 3: AI Enrichment
- `run_neeko_ai_enqueue()` — queues players needing AI regen
- Detects stale AI via `input_hash` comparison
- Edge function `generate-ai-worker` processes queue

#### Stage 4: Output Refresh
- `refresh_mv_edge_board()` — Materializes edge board view
- `market.build_market_watch_snapshot()` — Updates market signals

### 4.2 Cron Jobs

| Job ID | Schedule | Function | Purpose |
|--------|----------|----------|---------|
| 194 | Daily 1 AM | `run_afl_pipeline_controller_internal` | Master pipeline |
| 196 | Every 5 min | `run_neeko_ai_pipeline` | AI worker processor |
| 184 | Daily 2 AM | `refresh_projection_accuracy` | Accuracy metrics |

**⚠️ ISSUE**: Job 196 runs every 5 minutes but only processes queue if within 10 PM - 2 AM window (Melbourne)
- **Risk**: Queue can back up if jobs fail outside window

### 4.3 Pipeline Health Monitoring

**Tables**:
- `public.pipeline_runs` — Run history (run_id, status, duration)
- `public.pipeline_steps` — Step-level tracking
- `public.system_logs` — Error logging

**Views**:
- `admin.v_command_center_status` — Latest run status
- `public.v_pipeline_health` — Overall health check

**✅ GOOD**: Structured logging and monitoring in place
**⚠️ GAP**: No alerting on pipeline failures (requires external service)

## PART 6: CRITICAL FINDINGS

### 6.1 Formula Inconsistency ⚠️ HIGH

**Problem**: 3 different `neeko_rating` formulas exist:

1. **mv_player_projection** (CANONICAL — after migration `20260317072633`):
   ```sql
   projection*0.50 + confidence*0.20 + consistency*0.15 + value*0.10 - risk*0.05
   ```

2. **Frontend recomputation** (MarketWatchPage.tsx):
   ```typescript
   // Not computing neeko_rating, using database value ✅
   ```

3. **Old cache populate** (before migration):
   ```sql
   projection*0.55 + confidence*0.23 + consistency*0.17 + value*0.05
   ```

**Status**: ✅ RESOLVED in migrations (Phase 1-7), cache now COPIES value from MV

### 6.2 Breakeven Formula Issue ⚠️ MEDIUM

**Database** (migration `20260313132217`):
```sql
breakeven = COALESCE(pp.priced_at, ROUND(price / 10490, 1))
```
- Correct AFL Fantasy formula: `price / 10490`

**Frontend Override** (MarketWatchPage.tsx:38):
```typescript
breakeven: Math.round(r.projection_final ?? 0)
```

**❌ CRITICAL**: Frontend replaces accurate breakeven with projection!
- **Impact**: Market Watch shows wrong breakeven scores
- **Fix Required**: Change line 38 to `r.breakeven ?? Math.round(r.projection_final ?? 0)`

### 6.3 Value Score Computation ⚠️ MEDIUM

**Formula** (migration `20260317072745`):
```sql
value_score = LEAST(130, (projection_final - 60) / (price / 100000))
```

**Issue**: Requires `feature_price.value_score` to be populated by `refresh_projection_engine`
- Migration fixed this (Step 5 now computes real value)
- Frontend relies on this for ranking and filtering

**Status**: ✅ FIXED in pipeline (Phase 2)

### 6.4 Null Safety ⚠️ LOW (Recently Fixed)

**Previous Issue**: Unsafe `.map()` calls could crash on null data
**Fix Applied**: Changed to `(data || []).map()` in:
- `MarketWatchPremium.tsx` (lines 103, 119)
- `MobileRankingsTable.tsx` (line 417)

**Status**: ✅ RESOLVED
